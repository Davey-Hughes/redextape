# A list result's cells marked at a run's end — design

Return-value lane, PR 3 of 3 (PR 1, cut text read whole in a tooltip, merged as #194; PR 2, the result marked at a run's end, as #201). Base: main `f59ef8e`. PR 2's design, `2026-11-23-return-value-highlight-design.md`, holds the mark this one extends: when it shows (`result-mark.ts`'s `resultMarked`, unchanged here), its colours and its word.

## Intent

The user, 2026-11-21, on a result that is a reference: "yes if possible if the value is a reference we should point to the heap values there too"; and "if we don't have an example of that in the examples we should add it". PR 2 marks a list result by its pointer word alone (rxm `rr`, the value clif's main returns, TM field 0) and gives the λ view no mark for it. This PR lights the heap cells the list reaches, marks the λ term, and adds an example whose result is a list.

## The choices

The user chose each from browser mockups made of the app's real last frames, on 2026-11-25, answering "All a options":

1. **Reach: every cell the result reaches**, through each cell's tail and, for a list of lists, its head, nested lists' cells included.
2. **A lit cell: the tint and the edge on each cell, the word `result` on the pointer alone** (`rr`, the returned clif value, REG's field 0). Cells side by side share one box.
3. **A long list: the last frame carries every result cell, up to 64,** then a note with how many more there are.
4. **TM HEAP: mark what is on screen**, as PR 2 marks a field wider than REG's window; the window does not change.
5. **λ: a list over several rows is one block**, every row in the result's ground, one edge round them all, the word after the first row's text. A list on one row is marked as a number is.
6. **`[]`: the pointer's mark and the λ mark on `λn c. n`**, with no cell lit.
7. **The example: countdown(4) → `[4, 3, 2, 1]`**, a `while` loop, after *map and fold*.

## The design

### The frames

- **rxm:** at a halt whose `rr` is a list word, `RxmState::result` (`ResultCells`) names the cells it reaches, newest first, those the frame's `cells` holds (`shown`) and how many it reaches in all (`len`). The frame's cells take the newest `RxmWindow::result` (64 for the app) of them beside the window's own. `None` at every other frame, so only the halting frame pays.
- **clif:** the same, `ClifState::result`, from the value main returns when it is a list, under `ClifWindow::result`.
- **TM:** at a halt (not the overflow guard's), `TmState::result` names HEAP's runs, as materialized indices, from `tm::result_heap_runs`: the result read off the halted tapes by its type, each cell from its `@` to the next `@` or blank, runs side by side merged. `Session::tm_state` sets it; `None` at every other frame and for a result that is no list or is nil.

### The views

- **rxm and clif heaps:** each line of a cell in `result.shown` is `is-result`, tinted and edged on both sides, the edge closed at the first and last line of each run (`is-result-first`, `is-result-last`), its `aria-description` "part of the result". Where the list reaches cells the frame does not carry, those cells are among the older ones, so the older cells' note says how many of them are the result's, as one note, `+36 older, 36 of them result cells` (`1 of them a result cell` in the singular); where it reaches none, the note is `+N older` alone. Each line is padded the same, lit or not, so the box's side edges clear the glyphs and nothing moves at the step that lights it. In forced colours, which drop the tint and the edges, a lit line is outlined in `Highlight`, as no word stands beside it.
- **TM:** each run cut to HEAP's window is one `span.tm-result` box, as REG's field 0 is, with no word; HEAP's row says "the result's cells marked". In forced colours the box is outlined in `Highlight`; REG's keeps its word instead.
- **λ:** the root is marked whatever it is. On one row it is the run PR 2 draws; over several, each row is `.term-line.is-result-row`, tinted, with one edge round the block, the word after the first row's text. The block's left edge is a shadow off the mark strip's right side, since the strip is opaque and held at the view's edge.

## As built

- **An opened chip over several rows is marked too.** The λ rule no longer asks for a chip, so a numeral's chip opened over several rows at the run's end gets the block, as a list does.
- **Every λ row draws its `▸`/`▾` and its text where it draws them with no result marked**, as main does: the user ruled on 2026-11-26 that the block's left edge, a shadow off the mark strip's right side, may take a pixel of the first row's `▾` box, about 1px inside it, rather than every row giving up room after the strip. The ruling replaced two builds of that room: `4dc09f7`'s `EDGE_ROOM`, 4px after the strip on every row, which moved every row's text 4px right, and `d3b3cc4`'s narrower gutter, `calc(2ch - 4px)`, which kept the text where main has it and put each `▸`/`▾` 4px nearer it; neither is left. Each row keeps 3px at its end, marked or not (`.term-line` in `style.css`), and the rows 1px after them (`.term-rows`), 4px in all inside the 2ch the layout keeps clear, so it widens no term the layout fits and moves no glyph; the right edge, drawn on the row's end, then clears the widest row's last glyph where the term is wider than the view, a numeral chip's overline among them, and room on the block's rows alone would widen the term at the step that marks them. The pixel after the rows keeps the right edge inside a view at a fractional place, which clips the last pixel of rows that reach its edge: Firefox did so where the term fits the view, as countdown(4)'s last step does, and Chromium at the end of a sideways scroll.
- **A box's far edge has a pixel of room past it in a view scrolled to its end.** The λ block's bottom edge, a heap box's bottom edge and a HEAP box's right edge are drawn on the far side of the last row, line or cell, which lay on the content's end; in Chromium a view scrolled to its end can clip its content's last pixel, only where the view's top and height, or its left and width sideways, give `round(top) + round(height) > round(top + height)`, and not at every such place: it lost each of them at some. `.term-spacer`, which is content-box, and `.rxm-heap` have a pixel below the last row or line, and `.cells` one after the last cell, in every view at every step, marked or not, so nothing moves at the step that marks. Following and the keys take a λ view they bring to the last row down to the spacer's end, the pixel included. That pixel overflows a box within a pixel of fitting its content, at any step: such a box scrolls by up to 1px; End, ↓ or PageDown onto the last row of a λ view that holds every row with no pixel to spare scrolls it by that pixel and stops following, where main's keys scroll nothing; and, with classic scroll bars, such a box can draw a bar where main draws none, a cost the user ruled on 2026-11-27 to keep, as for the room at each row's end. Firefox drew each at every place tried; the near sides, and the TM box's bottom, which no scroll runs past, were never lost; REG's box has the word after it, so its right edge never lies on the row's end.
- **The λ word is dropped where the root's first row has no room for it, never wrapped**, as #201 drops the TM status line's `little-endian`. The row's text and the word's six columns must fit the columns the view shows without scrolling sideways (`wordFits` in `lambda-body.ts`): the width the layout keeps every row to, or, in a view narrower than the layout's 24-column floor, the fewer columns the view has, weighed when the lines are shown, so a list on one row that nearly fills the view, `[1, 2]` in `result-list.test.ts`'s case, keeps its ground, its edge and `data-marks`'s `result:` and loses the word, where the word would have scrolled the term sideways at the last step alone. In forced colours, which drop the ground and the block's edges, a result whose word is dropped is outlined in `Highlight`, whatever else the node is: the result's own edge rule names a result that is also linked and the contractum, which outranks a wordless result alone, so the forced rule names that result too. A wordless block's outline runs under the opaque strip on its left, so there its left edge is a 1px `Highlight` border on the strip's right side, whose width a negative margin gives back, so no text moves. A block's first row is the root's binders alone, `λn c.` for a list and `λf x.` for a numeral, which leave the word room wherever the view shows eleven columns; the rule weighs that row all the same, and in a narrower view drops the word. A resize alone lays nothing out in the λ view, so the word keeps what was weighed until the view next lays the term out.
- **A heap panel's box is a run of lit lines, not of cell numbers.** Two lit cells whose lines sit next to each other in the panel share a box though a cell between them is not among the lines the frame carries, as no line marks that gap either. On HEAP the cells lie on the tape as they are numbered, so a box there is a run of touching cells, and a cell the result does not reach between two of its cells parts them.
- **A result's cells are carried only where the result can be marked.** The walk from the result's word follows every List-tagged word, and a closure is a List-tagged cell of its tag and its environment, so the rxm leg, the clif leg and `Session::tm_state` name a result's cells only where the leg decodes the result to a value and prints it, the one result a view marks (`result-mark.ts`): a list of functions, which does not decode, and a list too large to print carry no result cells, and no unlit cell of either sits among a heap panel's lines. Only the frame that names the cells, the halt's, the `Ran` end's or the accept state's, pays for the decode and the capped print.
- **The TM's heap runs are found in Rust, cut in TypeScript.** `result_heap_runs` walks the halted HEAP by the result's type, so a Nat or a nil gives none; `tape.ts`'s `resultRuns` cuts them to the window the frame carries, and drops a run wholly off it. The TM view finds HEAP by the name the core gives the tape.
- **The TM names its runs on the accept state's frame.** The cursor reports `Halted` only from the step call after the one that reached the accept state, a call that takes no step, and the page's recorder takes one frame per step taken, so it never records a frame with that status. `Session::tm_state` names HEAP's runs where the cursor stands in an accept state, on the frame the recorder takes last, whose `status()` still reads `None`. The overflow guard's halt is no accept state, so it names none.
- **countdown(4) ends on every leg**, its value `[4, 3, 2, 1]`; under binary its TM HEAP window holds all four cells at the halt, so the view boxes them whole.
- **countdown(4)'s LLVM IR snapshots sit beside the other examples'**, `example-countdown.ll` and `example-countdown.opt.ll`, and `llvm-version.txt` names LLVM 23.1.5, the release that wrote every snapshot. The browser tier holds the views as built: `result-list.test.ts` runs countdown(4) and the other list cases in the app and a block in a λ body built by hand, `result-lambda.test.ts` a list on one row, and `result-stopped.test.ts`'s opened-chip case, which #201 held unmarked, holds sum_to(5)'s 15 opened over several rows as one block, the word after its first row.
